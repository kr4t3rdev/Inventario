# Specification: Ventas - Issues Críticos & Multitenancy

## 1. Issue #1: MultiTenant - TenantId Hardcodeado

### Requirement
Sistema DEBE obtener tenantId del usuario autenticado en todos los handlers de venta, no usar string vacío.

### Current Behavior
```typescript
// ❌ handlers.ts líneas 82, 138, 164, 247, 347
data: {
  tenantId: '',  // HARDCODED!
  // ... rest of data
}
```

### Expected Behavior
```typescript
// ✅ Debería ser:
const tenantId = requireTenant(user);
data: {
  tenantId,  // Del usuario
  // ... rest of data
}
```

### Scenarios

#### Scenario 1.1: Create Sale - Extract TenantId from User
```gherkin
Given usuario autenticado con tenantId "tenant-123"
And punto de venta "pv-001" existe en tenant-123
When POST /api/ventas con {"productos": [...], "puntoDeVentaId": "pv-001"}
Then response.status = 201
And venta.tenantId = "tenant-123" (NO "")
And factura.tenantId = "tenant-123"
```

#### Scenario 1.2: Tenant Isolation - User Cannot See Other Tenant Sales
```gherkin
Given usuario A con tenantId "tenant-a"
And usuario B con tenantId "tenant-b"
And venta creada en tenant-a
When usuario-b calls GET /api/ventas
Then response NO incluye venta de tenant-a
And response.status = 200, response.data = []
```

## 2. Issue #2: Idempotencia - Crear Keys Sin Validación

### Requirement
Sistema DEBE detectar y prevenir ventas duplicadas usando idempotency keys, retornando la venta existente en caso de reintento.

### Current Behavior
```typescript
// ❌ handlers.ts línea 56
if (anticipoCobroId && idempotencyKey) {
  await applyAnticipoAllocations(tx, [...], {
    idempotencyKey,  // Se pasa pero no se valida antes
    // ...
  })
}
// Key se acepta pero no se guarda/valida en Venta
```

### Expected Behavior
```typescript
// ✅ Debería:
// 1. Validar si idempotencyKey ya existe en DB
// 2. Si existe, retornar venta existente (sin duplicar)
// 3. Si no existe, crear + guardar key
// 4. Si viene sin key, generar UUID único
```

### Scenarios

#### Scenario 2.1: First Request with IdempotencyKey
```gherkin
Given cliente "cliente-01"
And idempotencyKey = "key-unique-12345"
When POST /api/ventas con {"productos": [...], "idempotencyKey": "key-unique-12345"}
Then response.status = 201
And venta.idempotencyKey = "key-unique-12345"
And venta creada en DB
```

#### Scenario 2.2: Retry with Same IdempotencyKey - Returns Existing
```gherkin
Given venta creada con idempotencyKey = "key-unique-12345"
And ventaId = "venta-001"
When POST /api/ventas con MISMO payload y idempotencyKey
Then response.status = 200 (OK, no 201)
And response.ventaId = "venta-001" (MISMO, no nuevo)
And venta_count en DB = 1 (NO 2)
```

#### Scenario 2.3: Request without IdempotencyKey - Generate UUID
```gherkin
Given request WITHOUT idempotencyKey field
When POST /api/ventas con {"productos": [...]}
Then venta.idempotencyKey = <auto-generated-uuid>
And venta creada normalmente
```

## 3. Issue #3: Stock - Dual Strategy (Legacy vs VentaItem)

### Requirement
Sistema DEBE usar ÚNICAMENTE `VentaItem` para tracking de stock. Deprecar `venta.productoId + venta.cantidad`.

### Current Behavior
```typescript
// ❌ Código soporta AMBAS simultáneamente
// Vieja: venta.productoId + venta.cantidad
// Nueva: venta.items[] (VentaItem)

// Cálculo confuso:
const ventasItems = await prisma.ventaItem.aggregate({...})
const ventasLegacy = await prisma.venta.aggregate({
  where: { productoId, puntoDeVentaId, items: { none: {} } },
  // ^^^^^^ Solo si NO tiene items
  _sum: { cantidad: true }
})
const ventasTotal = (ventasItems._sum.cantidad || 0) + (ventasLegacy._sum.cantidad || 0)
```

### Expected Behavior
```typescript
// ✅ Debería:
// 1. SIEMPRE usar VentaItem (nunca venta.productoId)
// 2. Verificar: venta.items es NON_EMPTY
// 3. Deprecar venta.productoId + venta.cantidad en SELECT
// 4. Migración: Convertir ventas legado a VentaItem en background
```

### Scenarios

#### Scenario 3.1: Create Sale with VentaItem - Stock Decremented
```gherkin
Given producto "prod-001" con stock = 100
And punto venta "pv-001"
When POST /api/ventas con {"productos": [{"productoId": "prod-001", "cantidad": 10}]}
Then venta.items = [VentaItem{productoId:"prod-001", cantidad:10}]
And venta.productoId = null (NO debe tener valor)
And StockUbicacion(punto_venta, pv-001, prod-001).delta = -10
```

#### Scenario 3.2: Calculate Available Stock - Use Only VentaItem
```gherkin
Given 5 VentaItem con producto "prod-001" en "pv-001", total cantidad = 20
And venta.productoId = null para todos
When validar stock disponible
Then cálculo = transferencias_entrada - transferencias_salida - 20
And NO incluye venta.cantidad legacy
```

#### Scenario 3.3: Pack Product - Parent Decremented via VentaItem
```gherkin
Given producto pack "pack-001" con cantidadEnPack = 5, stock = 50
And producto hijo "child-001" en pack
When POST venta con "child-001" cantidad = 12
Then venta.items[0] = VentaItem{productoId:"child-001", cantidad:12}
And producto pack stock -= floor(12/5) = 2
And StockUbicacion(almacen) decrementado por 2
```

## 4. Issue #4: Location Validation - StockUbicacion Sin Verificación

### Requirement
Sistema DEBE validar que ubicación existe y es válida ANTES de operar stock, no AFTER en servicio externo.

### Current Behavior
```typescript
// ❌ handlers.ts línea 269
await upsertStockUbicacion(tx, {
  productoId: item.productoId,
  tipoUbicacion: 'punto_venta',  // ¿Y si punto_venta no existe?
  ubicacionId: puntoDeVentaId,   // ¿Validado?
  modo: 'increment',
  delta: -item.cantidad
})
// Solo confía que puntoDeVentaId es válido porque pasó validación antes
```

### Expected Behavior
```typescript
// ✅ Debería:
// 1. Verificar PuntoDeVenta(pvId=puntoDeVentaId) existe
// 2. Verificar almacén existe si es productoPadre
// 3. Retornar error 404 si ubicación no válida
// 4. Guardar en transacción (rollback si falla)
```

### Scenarios

#### Scenario 4.1: Validate PuntoDeVenta Exists
```gherkin
Given puntoDeVentaId = "pv-invalid-999"
When POST /api/ventas con {"puntoDeVentaId": "pv-invalid-999", "productos": [...]}
Then response.status = 404
And response.error = "Punto de venta no encontrado"
And venta NO creada
```

#### Scenario 4.2: Validate Almacen Exists for Parent Product
```gherkin
Given producto "parent-001" con productoPadreId = null, almacenId = "alm-001"
And producto "child-001" con productoPadreId = "parent-001"
And almacenId "alm-001" NO existe en BD
When POST venta con "child-001"
Then transacción rollback
And response.status = 400
And response.error contiene "Almacén no disponible"
```

#### Scenario 4.3: StockUbicacion Operation Fails - Rollback Entire Transaction
```gherkin
Given venta being created in transaction
When upsertStockUbicacion retorna error (ubicación invalid)
Then venta.create también ROLLBACK
And cliente NO recibe venta
And response.status = 500
```

## 5. Issue #5: Error Handling - Errores Sin Rollback Explícito

### Requirement
Sistema DEBE hacer rollback explícito de transacciones en caso de error, con logging detallado.

### Current Behavior
```typescript
// ❌ Confía implícitamente en Prisma rollback
const venta = await prisma.$transaction(async (tx) => {
  // ... múltiples operaciones
  // Si una falla, ¿rollback automático?
  // No hay try-catch explícito dentro de tx
})
// catch afuera pero sin contexto
```

### Expected Behavior
```typescript
// ✅ Debería:
// 1. Try-catch DENTRO de transacción para manejo explícito
// 2. Log error con contexto (ventaId, userId, operación específica)
// 3. Return NextResponse con status + error message descriptivo
// 4. Retry logic para errores transitorios
```

### Scenarios

#### Scenario 5.1: Database Error - Rollback & Log
```gherkin
Given transacción de creación de venta en progreso
When prisma.venta.create retorna UNIQUE constraint error (ej: duplicate key)
Then transacción rollback automáticamente
And console.error loguea: "Error creando venta ventaId={id} usuario={userId}"
And response.status = 409
And response.error = "Venta duplicada o conflicto de datos"
```

#### Scenario 5.2: Stock Operation Fails - Partial Rollback
```gherkin
Given venta creada exitosamente
When StockUbicacion upsert falla (ej: ubicación inválida)
Then venta.delete() ejecutado (rollback)
And log: "Rollback venta {id} debido a error en stock"
And response.status = 500
And response.error descriptivo
```

#### Scenario 5.3: Factura Creation Fails - Full Transaction Rollback
```gherkin
Given venta creada, intentando crear factura
When crearFacturaParaVenta falla (ej: serie no disponible)
Then transacción completa rollback
And venta NO persiste
And response.status = 400
And response.error = "Serie de facturación no disponible"
```

## Summary: RFC 2119 Keywords

| Keyword | Applied To |
|---------|-----------|
| **MUST** | Validar tenantId de user, prevenir duplicados con idempotency key, usar solo VentaItem |
| **SHALL** | Retornar 404 si ubicación inválida, hacer rollback explícito |
| **SHOULD** | Loguear contexto detallado en errores, migrar stock legacy en background |
| **MAY** | Generar UUID si no viene idempotencyKey, retry automático en errores transitorios |

## Implementation Notes

1. **Orden de implementación**:
   - Issue #1 (MultiTenant) → core foundation
   - Issue #4 (Location Validation) → before stock operations
   - Issue #3 (Stock Unification) → refactor del flujo
   - Issue #2 (Idempotency) → add idempotencyKey schema + handler
   - Issue #5 (Error Handling) → envelope todos los anteriores

2. **DB Schema Changes**:
   - Añadir `idempotencyKey` a modelo `Venta` (unique, indexed)
   - Deprecar `Venta.productoId` (nullable, no usar nuevo)
   - Audit table para operaciones de stock (opcional pero recomendado)

3. **Backward Compatibility**:
   - Clients sin `idempotencyKey` → generar UUID
   - Queries legacy que usan `Venta.productoId` → seguir funcionando
   - API response → incluir `idempotencyKey` en respuesta

4. **Testing**:
   - Unit tests para cada scenario
   - Integration tests multitenancy
   - Load test para idempotency key performance
   - Rollback tests con simulación de errores
